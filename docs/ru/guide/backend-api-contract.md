# Соглашение с бэкендом

Эта страница — единый справочник по протоколу для интеграции бэкенда с `FlowUpload`. Приведённые запросы и ответы соответствуют встроенным HTTP-адаптерам: `createHttpUploadTransport`, `createHttpDownloadTransport`, `createHttpFileQueryTransport`. Если фронтенд передаёт пользовательские `transport`, `download-transport` или `query-transport`, адреса, имена полей и внешнюю обёртку ответа можно отображать самостоятельно; но адаптер в итоге обязан выдавать описанные здесь контракты компонента.

## Общие договорённости перед интеграцией

- Все управляющие интерфейсы (создание, проверка мгновенной загрузки, инициализация и слияние частей, запрос, архивация) используют JSON; успешный ответ должен быть ровно тем объектом, что показан на этой странице, без дополнительной обёртки `code`/`data`. Если в проекте уже есть обёртка `{ code, data }`, распаковывайте её в `parseResponse` (загрузка и запрос), `parseArchiveResponse` или `parseDownloadResponse` адаптера.
- Обычная загрузка использует `multipart/form-data`, boundary формирует браузер; не требуйте от фронтенда вручную задавать `Content-Type`.
- `auth.headers` отправляются как HTTP-заголовки; `auth.query` добавляется к каждому встроенному URL загрузки, скачивания и запроса. Бизнес-принадлежность не должна попадать в URL query — передавайте её в `data` или `query`.
- Любой статус `2xx` считается успехом; пустой ответ допустим только для обычной загрузки, удаления, отправки части и отмены архивации. Запрос, проверка мгновенной загрузки, создание записи, инициализация частей, слияние и создание либо опрос архива обязаны возвращать JSON.
- `fileId` — серверный идентификатор постоянного файла; он должен быть стабильным и пригодным для последующего удаления, скачивания и запросов. Не используйте клиентский `uid`. Если интерфейс предварительного создания не настроен, компонент генерирует UUID как начальный `fileId` и отправляет его вместе с загрузкой.
- Размер файла, `chunkSize` и размер части указываются в байтах; `chunkIndex` части начинается с `0`, номер страницы `currentPage` — с `1`.

## Процесс загрузки

Для обычного файла (не превышающего `normal-upload-threshold`, по умолчанию 10 MiB) порядок такой:

```text
выбор файла
  → POST createUrl (необязательно; назначить/подтвердить fileId)
  → POST checkUrl (необязательно; проверка мгновенной загрузки по SHA-256)
  → POST/PUT url (загрузка бинарных данных через multipart/form-data)
  → результат файла (success или processing)
```

Для большого файла (выше порога) с настроенными частями:

```text
выбор файла
  → POST createUrl (необязательно)
  → POST checkUrl (необязательно)
  → POST multipart.initUrl (создать или восстановить uploadId)
  → параллельные PUT multipart.chunkUrl (только незавершённые chunkIndex)
  → POST multipart.completeUrl (сервер проверяет и объединяет)
  → результат файла (success или processing)
```

При приостановке, удалении или отмене файла с частями фронтенд прерывает незавершённые HTTP-запросы браузера. Общую сессию нельзя удалять по инициативе одного пользователя; `multipart.cancelUrl` должен освобождать только аренду текущего вызывающего, а сервер очищает временные части после истечения сессии без аренд. При удалении постоянного файла вызывается `deleteUrl`. Только после того как `checkUrl` вернёт `state: "ready"` (или совместимый `exists: true`), фронтенд пропускает передачу байтов и использует возвращённый `file`.

### Запросы и ответы по каждому интерфейсу загрузки

| Операция | HTTP-запрос | Тело / заголовки | Успешный ответ |
| --- | --- | --- | --- |
| Предварительное создание | `POST createUrl` | JSON: `FileMeta` + `data` | `{ "fileId": "file_123" }` |
| Проверка мгновенной загрузки | `POST checkUrl` | JSON: `FileMeta` | `{ "state": "missing" }`, `{ "state": "ready", "file": UploadSuccessResult }` или состояние общей загрузки |
| Обычная загрузка | `POST` (по умолчанию) или `PUT url` | `multipart/form-data`: поле файла, `fileId`, поле JSON-строки data | `UploadSuccessResult` или пустой ответ |
| Инициализация частей | `POST multipart.initUrl` | JSON: `FileMeta` + `chunkSize`, `totalChunks`, `data` | `{ "uploadId": "upload_123", "state": "uploading", "uploadedChunks": [0, 1] }` |
| Отправка части | `PUT multipart.chunkUrl` | тело — необработанные байты части; заголовки ниже | пустой ответ или любой корректный JSON (тело не используется) |
| Завершение частей | `POST multipart.completeUrl` | JSON: `fileId?`, `sha256?`, `data` | `UploadSuccessResult` |
| Отмена частей | `DELETE multipart.cancelUrl` | без тела | может быть пустым |
| Удаление файла | `DELETE deleteUrl` | без тела | может быть пустым |

#### `FileMeta`: метаданные для предварительного создания, проверки и инициализации частей

```json
{
  "fileId": "4cb11903-6b4d-4c84-b988-a7c7d7a9f88f",
  "name": "invoice.pdf",
  "size": 1048576,
  "mimeType": "application/pdf",
  "lastModified": 1722470400000,
  "sha256": "необязательно, 64-символьная hex-строка"
}
```

`sha256` присутствует только при включённой проверке мгновенной загрузки или при включённой докачке (`resume`) для большого файла. Запрос предварительного создания добавляет к этим полям `data`, а инициализация частей ещё и `chunkSize`, `totalChunks` и `data`:

```json
{
  "fileId": "file_123",
  "name": "archive.zip",
  "size": 26214400,
  "mimeType": "application/zip",
  "lastModified": 1722470400000,
  "sha256": "...",
  "chunkSize": 1048576,
  "totalChunks": 25,
  "data": {
    "belongId": "order-1001",
    "belongType": "order",
    "extra": { "category": "invoice" }
  }
}
```

`data` берётся из prop `data` компонента, а `belong-id`, `belong-type` и `extra` перекрывают одноимённые поля. По умолчанию поля обычной загрузки называются `file` и `data`, их можно изменить через `file-field-name` и `data-field-name`:

```text
Content-Type: multipart/form-data; boundary=…

file: <бинарный файл>
fileId: file_123
data: {"belongId":"order-1001","belongType":"order","extra":{"category":"invoice"}}
```

## Мгновенная загрузка и параллельная загрузка одного содержимого

Сервер обязан разделять «объект содержимого» и «бизнес-ссылку на файл»: объект содержимого однозначно определяется парой `sha256` и `size`, алгоритмом хеширования и версией политики хранения; бизнес-ссылка хранит текущего пользователя, тенант, бизнес-принадлежность и права на скачивание. Нельзя только по совпадению SHA-256 возвращать вызывающему `fileId`, URL или информацию о существовании чужого файла.

Рекомендуемый ответ `checkUrl` — дискриминированный `state`, причём `ready` допустим только тогда, когда содержимое полностью загружено и текущий вызывающий вправе создать или прочитать ссылку:

```json
{ "state": "ready", "file": { "fileId": "file_123", "status": "success" } }
```

Если содержимого ещё нет, верните `{ "state": "missing" }`. Когда другой пользователь передаёт то же содержимое, верните состояние ниже; фронтенд всё равно вызовет идемпотентный `initUrl` за авторитетным списком отсутствующих частей, поэтому `uploadId` и `uploadedChunks` необязательны и служат только для диагностики и отображения:

```json
{ "state": "uploading", "uploadId": "upload_123", "uploadedChunks": [0, 1], "retryAfterMs": 1000 }
```

Если другой запрос уже начал слияние или асинхронную постобработку, верните `{ "state": "merging", "uploadId": "upload_123", "retryAfterMs": 1000 }`.

Для совместимости со старыми версиями компонент по-прежнему принимает `{ "exists": false }` и `{ "exists": true, "file": ... }`; новые серверы должны перейти на `state`. Проверка мгновенной загрузки выполняется до `createUrl`, чтобы попадание в общее содержимое не создавало осиротевшую бизнес-запись. После промаха `createUrl` должен быть идемпотентным и при завершении создавать или подтверждать бизнес-ссылку текущего вызывающего.

`initUrl` — атомарная операция «получить или создать сессию по содержимому», её нельзя реализовать как отдельные чтение и вставку. Рекомендуется уникальное ограничение по ключу содержимого либо создание в короткой транзакции или под распределённой блокировкой. Интерфейс обязан всегда возвращать авторитетное состояние одной и той же активной сессии:

```json
{
  "uploadId": "upload_123",
  "state": "uploading",
  "uploadedChunks": [0, 1]
}
```

Если `state` опущен, компонент считает его равным `uploading`. Когда сессия уже сливается или обрабатывается, верните `merging` или `processing`: фронтенд перестаёт писать части и вызывает идемпотентный `completeUrl`, а бэкенд возвращает `processing` или итоговый результат файла.

#### PUT-запрос части

Двоичные данные части не заворачиваются в `FormData` или JSON — всё тело HTTP-запроса и есть эта часть. Плейсхолдеры `{uploadId}` и `{index}` в URL подставляются и кодируются. Бэкенд находит и проверяет часть по следующим заголовкам:

| Заголовок | Значение |
| --- | --- |
| `Content-Type` | `application/octet-stream` |
| `X-Upload-Id` | идентификатор текущей сессии частей |
| `X-Chunk-Index` | номер части, начиная с 0 |
| `X-Total-Chunks` | общее число частей файла |
| `X-Chunk-Size` | настроенный размер части в байтах |
| `X-File-Name` | исходное имя файла после `encodeURIComponent` |
| `X-File-Size` | общий размер исходного файла в байтах |
| `X-File-Id` | необязательно, идентификатор постоянного файла |
| `X-File-Sha256` | необязательно, SHA-256 всего файла |

`uploadedChunks`, возвращённый инициализацией, — это массив уже успешно сохранённых номеров частей, начиная с 0; фронтенд отправляет только отсутствующие индексы. Таблица частей должна иметь уникальное ограничение по `(uploadId, chunkIndex)`, а объектное хранилище — использовать фиксированные ключи и условную запись; повторная отправка идентичной по байтам части должна возвращать успех, а расхождение длины, дайджеста или индекса обязано отклоняться. Бэкенд должен позволять интерфейсу слияния вернуть успех только после того, как все индексы на месте и файл прошёл проверку.

## Завершение слияния, ошибки и очистка

Завершённость загрузки определяется атомарным результатом серверного `completeUrl`, а не тем, что браузер выполнил все `PUT`. `completeUrl` должен быть идемпотентным и использовать блокировку слияния по каждому `uploadId` или условное обновление состояния, чтобы слияние выполнял ровно один запрос:

1. В транзакции убедиться, что сессия в состоянии `uploading`, и атомарно перевести её в `merging`; если она уже `ready`, вернуть имеющийся результат, если уже `merging` — вернуть `processing`.
2. Проверить наличие каждого индекса в диапазоне `0..totalChunks-1`, размер каждой части (кроме последней) и необязательный дайджест части; при отсутствующих частях вернуть `409` со стабильным бизнес-кодом `MISSING_CHUNKS`.
3. Слить части по порядку индексов во временный объект, заново вычислить SHA-256 всего файла и сравнить с `FileMeta.sha256`; при расхождении вернуть неповторяемую ошибку `422 HASH_MISMATCH`.
4. Атомарно опубликовать итоговый объект, пометить содержимое как `ready` и создать или подтвердить бизнес-ссылку текущего вызывающего; только после этого вернуть `UploadSuccessResult`.

Рекомендуемая обработка ошибок: `408`, `429`, `5xx` и обрыв сети можно повторять; `401`, `403`, `400`, конфликты метаданных частей и несовпадение хеша повторять вслепую нельзя. Перед повтором клиент должен снова вызвать `initUrl`, чтобы учесть ситуацию «части сохранены, но ответ потерян». При неудачном слиянии сохраняйте восстановимые части и фиксируйте код ошибки, причину, `uploadId`, отпечаток содержимого, индекс части и число попыток; сессии используют аренду или время последней активности, а асинхронная очистка выполняется только после освобождения всех аренд и истечения сессии.

#### `UploadSuccessResult`: результат загрузки, попадания мгновенной загрузки и слияния

```json
{
  "status": "success",
  "fileId": "file_123",
  "name": "invoice.pdf",
  "size": 1048576,
  "mimeType": "application/pdf",
  "url": "https://cdn.example.com/files/file_123",
  "thumbnailUrl": "https://cdn.example.com/files/file_123/thumb"
}
```

Все поля необязательны, но производственный интерфейс должен возвращать как минимум `fileId`; `name`, `size`, `mimeType`, `url` и `thumbnailUrl` записываются в строку файла на клиенте. Если `status` отсутствует или равен `success`, компонент сообщает об успешной загрузке; при `processing` компонент сохраняет состояние «сервер обрабатывает», пока хост не обновит результат запроса.

## Скачивание и архивация на сервере

### Скачивание одного файла

`GET downloadUrl`, где плейсхолдер `{fileId}` заменяется идентификатором постоянного файла. У запроса нет JSON-тела, а успешный ответ обязан быть двоичным содержимым файла. Встроенный адаптер читает его как Blob и определяет имя для сохранения в таком порядке:

1. `Content-Disposition: attachment; filename*=UTF-8''...`
2. `Content-Disposition: attachment; filename="..."`
3. поле `name` из списка файлов

Рекомендуемый ответ:

```http
HTTP/1.1 200 OK
Content-Type: application/pdf
Content-Disposition: attachment; filename*=UTF-8''invoice.pdf

<binary bytes>
```

Не возвращайте с этого интерфейса JSON с Base64 или `{ url }`. Если для скачивания сначала нужно получить подписанный URL, реализуйте собственный `DownloadTransport.downloadFile` и верните `{ url, fileName? }`.

### Пакетные задачи архивации

Пакетное скачивание собирается бэкендом асинхронно. Интерфейсы создания, опроса и отмены архива:

| Операция | HTTP-запрос | body | Успешный ответ |
| --- | --- | --- | --- |
| Создание задачи | `POST archive.createUrl` | JSON `ArchiveCreateInput` | `ArchiveTask` |
| Опрос задачи | `GET archive.taskUrl` | без body | `ArchiveTask` |
| Отмена задачи | `DELETE archive.cancelUrl` | без body | может быть пустым |

«Скачать выбранное» и «Скачать всё» по умолчанию отправляют только список идентификаторов постоянных файлов:

```json
{ "fileIds": ["file_123", "file_456"] }
```

Если задан `all-download-scope`, компонент вместо длинного списка идентификаторов использует серверный диапазон запроса:

```json
{
  "scope": {
    "type": "server-query",
    "queryKey": "order-attachments",
    "query": { "orderId": "order-1001", "includeArchived": false }
  }
}
```

Другая форма явного диапазона — `{ "type": "file-ids", "fileIds": ["file_123"] }`. `DownloadTransport.createArchive` также принимает необязательное поле `archiveName`, но компонент сейчас его не задаёт; если нужно фиксированное имя архива, задайте его в пользовательском адаптере или на сервере. Сервер должен принимать только те файлы, к которым у вызывающего есть доступ; доверять присланным идентификаторам нельзя.

Формат ответа `ArchiveTask` приведён ниже; `status` может быть только `pending`, `processing`, `success`, `failed` или `canceled`:

```json
{
  "taskId": "archive_123",
  "status": "processing",
  "progress": 45,
  "fileName": "order-1001-attachments.zip"
}
```

Ответ успешного опроса обязан содержать `downloadUrl`:

```json
{
  "taskId": "archive_123",
  "status": "success",
  "progress": 100,
  "fileName": "order-1001-attachments.zip",
  "downloadUrl": "https://storage.example.com/signed/archive_123"
}
```

Неудачная задача должна предоставлять отображаемое поле `errorMessage`. Фронтенд опрашивает только состояния `pending` и `processing`; при `success` начинается скачивание по `downloadUrl`, любое другое терминальное состояние завершает процесс.

## Запрос файлов

С настроенным `createHttpFileQueryTransport({ queryUrl })` компонент использует `POST queryUrl`. Запрос выполняется при первом монтировании, при глубоком изменении `extra`, при смене страницы, после успешной загрузки и при перечитывании списка после успешного удаления; новый запрос отменяет предыдущий, поэтому бэкенд должен корректно обрабатывать отключение клиента.

### Запрос

```json
{
  "query": {
    "belongId": "order-1001",
    "belongType": "order",
    "extra": {
      "keyword": "invoice",
      "status": "success"
    }
  },
  "pagination": {
    "enabled": true,
    "currentPage": 1,
    "pageSize": 20
  }
}
```

`query` строится по тем же правилам, что и `data` при загрузке: prop `data` служит основой, а `belongId`, `belongType` и `extra` перекрывают одноимённые поля. `pagination.enabled` присутствует всегда:

| Режим | pagination в запросе | pagination в ответе |
| --- | --- | --- |
| Без пагинации | `{ "enabled": false }` | `{ "enabled": false }` |
| С пагинацией | `{ "enabled": true, "currentPage": 1, "pageSize": 20 }` | `{ "enabled": true, "currentPage": 1, "pageSize": 20, "total": 42 }` |

В ответе с пагинацией `currentPage` и `pageSize` должны быть значениями, которые сервер реально применил (например, исправленный номер страницы за пределами диапазона), а `total` — общим числом записей по текущему `query`.

### Ответ и элементы файлов

Полный ответ пагинированного запроса:

```json
{
  "files": [
    {
      "fileId": "file_123",
      "name": "invoice.pdf",
      "size": 1048576,
      "type": "application/pdf",
      "status": "success",
      "percent": 100,
      "url": "https://cdn.example.com/files/file_123",
      "thumbnailUrl": "https://cdn.example.com/files/file_123/thumb"
    }
  ],
  "pagination": {
    "enabled": true,
    "currentPage": 1,
    "pageSize": 20,
    "total": 42
  }
}
```

`files` должен быть массивом, а `pagination.enabled` в ответе обязан совпадать с запросом. Каждый элемент соответствует `UploadUserFile`: единственное жёсткое требование — `name`, но чтобы файлы можно было удалять и скачивать, бэкенд должен возвращать как минимум `fileId`, `name`, `size`, `type`, `status: "success"` и `percent: 100`. Для файлов, загруженных с сервера, не возвращайте браузерное поле `file` и не обязаны возвращать `uid`; компонент подставит локальный `uid`.

## Рекомендации по ошибкам и идемпотентности

- Для обычной загрузки, частей, слияния и создания архива реализуйте идемпотентность по `fileId`, `uploadId + chunkIndex` и `taskId`, чтобы сетевой повтор не создавал дубликаты объектов или частей.
- `DELETE deleteUrl`, `DELETE multipart.cancelUrl` и `DELETE archive.cancelUrl` рекомендуется делать идемпотентными: если ресурса уже нет, можно вернуть `204` или успешный статус, чтобы повтор клиента не превращался в ошибку.
- Для ответов вне диапазона 2xx компонент сохраняет HTTP-статус и считает `408`, `429` и `5xx` повторяемыми; бизнес-ошибки, которые нельзя повторять, должны возвращать подходящий `4xx`. Пользовательские адаптеры могут выбрасывать `{ code, message, retriable, status?, cause? }` для более точной семантики ошибок.
- Формат JSON для ошибок `403`, `404`, `409`, `413` и подобных определяет бизнес; встроенные адаптеры не разбирают их тело. В журналах связывайте `fileId`, `uploadId` и `taskId`, не записывайте двоичные данные файлов и чувствительные данные аутентификации.
